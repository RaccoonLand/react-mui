# 5. usePipelineQuery & usePipelineMutation

Thin wrappers over `@tanstack/react-query` that plug in the pipeline envelope parser, the loading adapter, and the
toast adapter.

- **Package:** `@raccoonland/pipeline-client`
- **File:** `src/hooks/usePipelineRequest.ts`

## Shared options

Both hooks accept the same UX knobs via [`PipelineRequestOptions`](../src/hooks/usePipelineRequest.ts):

```ts
type PipelineRequestOptions = {
  showGlobalLoader?: boolean   // default true  — routes withLoading with scope: 'global'
  loadingMessage?: string      // optional text shown by the global backdrop
  showErrorToast?: boolean     // default true  — call toast.showError on failure
  showWarningToast?: boolean   // default true  — call toast.showWarning per warning on success
}
```

## `usePipelineQuery`

```ts
usePipelineQuery<TData, TQueryKey>({
  queryKey,
  queryFn,           // may return TData OR PipelinePayload<TData>
  ...standardReactQueryOptions,
  ...pipelineRequestOptions,
})
```

- `queryFn` receives the standard `QueryFunctionContext` and must return either the raw data or a
  `PipelinePayload<TData>` (see [`6.Errors`](6.Errors.md)).
- Warnings are toasted **outside** of `queryFn` so retries don't produce duplicate notifications.
- Errors are toasted from a `useEffect` gated by `errorUpdatedAt` — retries and effect-double-invocation under
  `<StrictMode>` still produce a single toast.

## `usePipelineMutation`

```ts
usePipelineMutation<TData, TVariables>({
  mutationFn,        // may return TData OR PipelinePayload<TData>
  ...standardReactQueryOptions,
  ...pipelineRequestOptions,
})
```

- Errors are toasted immediately inside the executor because mutations default to `retry: 0` in this monorepo's
  `queryClient` config — no risk of duplicate toasts across retries.

## PipelinePayload

If a `queryFn` / `mutationFn` needs to surface warnings that the raw `fetchPipeline` already produced, wrap the
result with [`createPipelinePayload(result)`](../src/pipelinePayload.ts) and return it. The executor unwraps
`__pipelinePayload` markers automatically:

```ts
mutationFn: async (input) => {
  const result = await fetchPipeline<UserDto>('/api/users/create', { method: 'POST', data: input })
  return createPipelinePayload(result)
},
```

Plain-data return values bypass the warning fan-out; use `PipelinePayload` only when you actually have warnings.

## Cancellation

Both hooks understand `AbortError` / axios `CanceledError` via `isAbortError` and neither toast nor log them. Return
those to React Query so cache eviction stays sane.

## Example

```tsx
const users = usePipelineQuery<UserDto[], ['users']>({
  queryKey: ['users'],
  queryFn: async () => {
    const result = await fetchPipeline<UserDto[]>('/api/users/list')
    return createPipelinePayload(result)
  },
  loadingMessage: t('loadingUsers'),
})

const createUser = usePipelineMutation<UserDto, UserInput>({
  mutationFn: async (input) => {
    const result = await fetchPipeline<UserDto>('/api/users/create', { method: 'POST', data: input })
    return createPipelinePayload(result)
  },
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ['users'] }),
})
```

## Error routing summary

| Thrown from `fetchPipeline`             | Toast                                         | Monitoring          |
|-----------------------------------------|-----------------------------------------------|---------------------|
| `PipelineApiError`                      | one toast per `errors[]` message              | not reported        |
| `NetworkError`                          | `messages.networkError`                       | `kind: 'network'`   |
| `InvalidPipelineResponseError`          | `messages.invalidPipelineResponse`            | `kind: 'invalid-pipeline-response'` |
| Anything else (unexpected)              | `messages.unknownError`                       | `kind: 'unknown'`   |
| Abort / cancel                          | none                                          | none                |

The `messages` come from [`PipelineUiMessagesProvider`](7.PipelineUiMessages.md).
