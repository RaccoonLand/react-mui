# 6. Errors & PipelinePayload

The exception types thrown by `fetchPipeline` and the sidecar `PipelinePayload` marker.

- **Package:** `@raccoonland/pipeline-client`
- **Files:** `src/errors.ts`, `src/pipelinePayload.ts`

## `PipelineApiError`

Thrown when the server's `PipelineResponse` has a non-empty `errors` array — regardless of HTTP status.

```ts
class PipelineApiError extends Error {
  readonly errors: PipelineMessage[]
  readonly status: number
}
```

- `message` is a joined summary of the non-empty `errors[].message`s (fallback: `"Pipeline request failed"`).
- `errors` preserves the coded array; hooks iterate over it to toast each entry.
- `status` is the HTTP status observed on the response, useful for retry/log decisions but **not** used for
  branching by the hooks (branching is done on `PipelineApiError` presence).

## `NetworkError`

Thrown when axios reports an error with no `response` — DNS failure, offline, CORS block, connect timeout.

```ts
class NetworkError extends Error {
  constructor(message = 'Network request failed')
}
```

Hooks translate this into `messages.networkError` at the toast layer, so end users see a localized string, not the
raw `"Network request failed"`.

## `InvalidPipelineResponseError`

Thrown when the HTTP body arrived but doesn't look like a `PipelineResponse` (e.g. an HTML error page from a proxy,
or a stray `{ data: {...} }` from a misconfigured endpoint).

```ts
class InvalidPipelineResponseError extends Error {
  readonly status: number
  readonly body: unknown
}
```

Log the `body` when triaging incidents — it will usually make the misconfiguration obvious.

## `isAbortError`

Cross-runtime helper that catches both the DOM `AbortError` and axios `CanceledError` / `ERR_CANCELED`:

```ts
export function isAbortError(error: unknown): boolean
```

Every caller that toasts or reports errors must consult this first — cancellations are intentional and must not
appear in the UI or the error tracker.

## `PipelinePayload<T>`

An in-band marker that lets a `queryFn` / `mutationFn` return **data + warnings** to the hooks executor.

```ts
export type PipelinePayload<T> = {
  __pipelinePayload: true
  data: T
  warnings: PipelineMessage[]
}

export function createPipelinePayload<T>(result: PipelineResult<T>): PipelinePayload<T>
export function isPipelinePayload<T>(value: unknown): value is PipelinePayload<T>
```

Why not always return `PipelineResult<T>` directly? Because most callers do not have warnings, and forcing them to
unwrap `.data` on every mutation onSuccess handler is friction. `PipelinePayload` is opt-in: wrap only when you
want the executor to toast warnings for you.

## Design notes

- Errors are **plain classes**, not discriminated unions. Discriminating by `instanceof` reads naturally in
  try/catch and pattern-matches with `if` chains at call sites.
- Errors never carry the axios `config` or `response` — those can contain tokens and PII. Callers that need the
  original response inspect `body` on `InvalidPipelineResponseError` or catch the raw axios error before
  `parsePipelineResponse` reaches it (advanced use).
