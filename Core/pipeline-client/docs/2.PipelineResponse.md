# 2. PipelineResponse & PipelineResult

The wire envelope from a RaccoonLand backend and the parsed shape delivered to app code.

- **Package:** `@raccoonland/pipeline-client`
- **File:** `src/types/pipeline.ts`

## Wire type — `PipelineResponse<T>`

```ts
export type PipelineResponse<T> = {
  result: T
  errors: PipelineMessage[]
  warnings: PipelineMessage[]
  statusHint?: number | null
}

export type PipelineMessage = {
  code: string
  message: string
}
```

- `result` — the endpoint payload. Use `T | null` when the endpoint may return a null result (e.g. get-by-id).
- `errors` — coded, human-readable failures. **Non-empty implies the request failed**, regardless of HTTP status.
- `warnings` — coded, non-blocking notices attached to a successful response.
- `statusHint` — optional HTTP status the server would recommend if it were rendering the response itself. Useful
  for hosts that translate envelopes into REST responses.

## Parsed type — `PipelineResult<T>`

```ts
export type PipelineResult<T> = {
  data: T
  warnings: PipelineMessage[]
}
```

`PipelineResult<T>` is what `fetchPipeline` returns on success. There is no `errors` field on purpose — a non-empty
`errors` on the wire is turned into a thrown [`PipelineApiError`](6.Errors.md) by the parser, so success is the
absence of errors.

## Parse rules

Implemented in `parsePipelineResponse` (`src/client.ts`):

1. If the body is missing `errors` or `warnings` arrays, throw `InvalidPipelineResponseError` (protocol violation).
2. Normalize each message to `{ code: string, message: string }`, defaulting `code` to `Unknown` and `message` to
   `"Pipeline request failed"` if the server omitted them.
3. If `errors.length > 0` → throw `PipelineApiError(errors, status)`.
4. Otherwise return `{ data: normalizePipelineData(result), warnings: normalizePipelineData(warnings) }`.

Step 4 uses [`normalizePipelineData`](../src/normalizePipelineData.ts) to lowercase leading letters recursively.
This aligns the payload shape with typical TypeScript conventions when the server uses PascalCase.

## Warnings vs errors — decision matrix

| Case                           | Envelope                                 | Client behavior            |
|--------------------------------|------------------------------------------|----------------------------|
| Success, no notices            | `errors: []`, `warnings: []`             | Return `data`; toast none. |
| Success with notices           | `errors: []`, `warnings: [...]`          | Return `data`; toast each warning (opt-in). |
| Explicit business failure      | `errors: [...]`                          | Throw `PipelineApiError`; toast each error. |
| Server crash returning envelope| `errors: [{ code: 'SYSTEM_ERROR', ... }]`| Same as business failure — server chose to represent it as a coded error. |
| Non-envelope 5xx / HTML page   | body doesn't match the envelope          | Throw `InvalidPipelineResponseError`. |
| Network / DNS / CORS           | no HTTP response at all                  | Throw `NetworkError`.      |

## Design notes

- Nullability lives in `T`, not in a separate flag. If your endpoint returns "not found" as `null`, type it as
  `PipelineResult<PersonDetail | null>` — the parser will happily hand you `null` for `data`.
- The parser also fires for **error responses** whose body still matches the envelope (see `client.ts` catch branch).
  This means a 4xx that returns a proper `errors` array becomes a `PipelineApiError` rather than a raw axios error.
