# 4. ConfirmProvider

Imperative, promise-based confirmation dialog with a queue.

- **Package:** `@raccoonland/feedback`
- **File:** `src/confirm/ConfirmProvider.tsx`

## Public API

```ts
type ConfirmOptions = {
  title:       ReactNode
  message?:    ReactNode
  confirmText?: string
  cancelText?:  string
  destructive?: boolean   // switches primary button to error color + warning icon tone
}

const confirm: (options: ConfirmOptions) => Promise<boolean>
```

```ts
const confirm = useConfirm()

const ok = await confirm({
  title: t('confirmDeleteTitle'),
  message: t('confirmDeleteMessage', { name }),
  confirmText: t('delete'),
  cancelText: t('cancel'),
  destructive: true,
})

if (ok) {
  await deleteItem(id)
}
```

## Queue semantics

If a confirm is requested while another is already open, the new request is **queued** — its promise stays pending
until the earlier dialog resolves. The queue drains FIFO.

Side effects (setting the "active" request) happen **outside** `setState` so that Strict Mode's double-invocation
of state initializers cannot enqueue twice or drop a resolver.

## Cancellation

- Clicking Cancel resolves the promise with `false`.
- Clicking outside the dialog / pressing Escape → same as Cancel.
- The AppDialog's Enter-to-confirm shortcut (see `AppDialog`) resolves with `true` unless Cancel is focused.
- There is intentionally no `dismiss()` external API; call `confirm()` again with a fresh state to override.

## Composition with destructive actions

`destructive: true` swaps the confirm button to `color="error"` and the header icon to a warning tone. Use it for
delete / remove / drop actions. Pair with a specific error toast on failure:

```ts
try {
  if (!(await confirm({ title: 'Delete?', destructive: true }))) return
  await deleteThing(id)
  showSuccess(t('deleted'))
} catch (error) {
  // pipeline-client already surfaces server errors — nothing extra here.
}
```

## Design notes

- The dialog itself is rendered by [`ConfirmDialog`](../src/confirm/ConfirmDialog.tsx), which composes
  [`AppDialog`](5.Overlay.md). Keeping the presentational layer separate keeps the provider testable without a
  DOM.
- The provider's `value` (`{ confirm }`) is memoized on the stable `confirm` callback, so consumers do not
  re-render on unrelated state churn inside the provider.
