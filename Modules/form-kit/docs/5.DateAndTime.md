# 5. Date & time controls

Gregorian pickers via `@mui/x-date-pickers` and a Jalali (Persian) picker via `react-multi-date-picker` — with a
shared value-format vocabulary.

- **Package:** `@raccoonland/form-kit`
- **Files:** `src/FormDatePickers.tsx`, `src/FormPersianDatePicker.tsx`

## FormDateLocalizationProvider

Thin wrapper over MUI's `LocalizationProvider` bound to `AdapterDayjs`. Mount it above every form that uses the
Gregorian pickers (or use your own `LocalizationProvider`).

```tsx
<FormDateLocalizationProvider adapterLocale={locale === 'fa' ? 'fa' : 'en'}>
  <form>{...}</form>
</FormDateLocalizationProvider>
```

## Value formats

Both Gregorian and Persian pickers agree on a small vocabulary:

| `valueFormat` | Stored shape                        | Notes                                      |
|---------------|-------------------------------------|--------------------------------------------|
| `'iso'`       | Full ISO string (`toISOString()`)    | Default for `FormDateTimePicker`.          |
| `'date'`      | `YYYY-MM-DD`                        | Default for `FormDatePicker`.              |
| `'time'`      | `HH:mm`                             | Default for `FormTimePicker`.              |
| `'jalali'`    | `YYYY/MM/DD` on the Jalali calendar | Persian picker default.                    |

## FormDatePicker / FormTimePicker / FormDateTimePicker

Bound to MUI X pickers. Value round-trips through `dayjs` — parse on read, format on write.

```tsx
<FormDatePicker<Form> name="startDate" label={t('startDate')} />
<FormTimePicker<Form> name="startTime" label={t('startTime')} />
<FormDateTimePicker<Form> name="publishAt" label={t('publishAt')} valueFormat="iso" />
```

All three accept `datePickerProps` / `timePickerProps` / `dateTimePickerProps` for pass-through to the underlying
MUI X component, and `textFieldProps` for the inner TextField.

Empty values are stored as `null`. Invalid dayjs values are also coerced to `null` on write so form state never
contains "invalid date" strings.

## FormPersianDatePicker

Jalali calendar with optional range mode.

```tsx
<FormPersianDatePicker<Form>
  name="dueDate"
  label={t('due')}
/>

<FormPersianDatePicker<Form>
  name="reportingPeriod"
  label={t('period')}
  range
  rangeLabels={{ start: t('from'), end: t('to') }}
/>
```

### Range mode

Renders **two independent pickers** side by side. Each side has its own month/year navigation, so a user can pick
a start date in one month and an end date in another year without fighting the calendar. The two pickers agree on
range validity:

- Start picker's `maxDate` is the current end (so it can never move past the end).
- End picker's `minDate` is the current start (so it can never move before the start).
- If the user moves the start after the end, the end is cleared — no silent overwriting.

Form state shape: `FormPersianDateRangeValue` = `[string | null, string | null]`.

### Theming

`react-multi-date-picker` ships with its own default look. The kit re-themes it via a shared `<GlobalStyles>` bound
to a stable class name (`rl-persian-datepicker`). All pickers on a page share the same generated stylesheet — no
per-instance selector duplication — and the styles re-derive only when `raccoon` tokens change (i.e. on theme mode
switch).

### Interop caveats

`react-multi-date-picker` and `react-date-object` are CJS packages. This file uses `resolveDefaultExport` to
handle the `{ default: Component }` shape Vite ESM sometimes produces, and the sample's Vite config lists both
in `optimizeDeps.needsInterop` so dev-mode pre-bundling matches production.

## Design notes

- `FormPersianDatePicker` stores values as **strings**, not `DateObject` instances. This keeps form state
  serializable (safe to persist in a draft, safe to send over the wire) and does not tie the form to the picker's
  runtime.
- The kit intentionally does not expose a "single picker that supports both calendars via a prop" — that would
  either bloat the bundle for LTR-only apps or hurt DX. Choose the Gregorian pickers or the Persian picker per
  form.
