# 2. LayoutShellConfig

The config object the host passes to `BackofficeLayout`. It lives in a context (`LayoutShellProvider`) so every
shell component can read it without prop drilling.

- **Package:** `@raccoonland/layout`
- **File:** `src/types.ts`, `src/LayoutShellContext.tsx`

## Shape

```ts
export type LayoutShellConfig = {
  navigation: LayoutNavItem[]
  brand: LayoutBrand
  direction: 'ltr' | 'rtl'
  labels: LayoutChromeLabels
  settingsPath?: string           // default '/settings/layout'
  user: {
    isLoading: boolean
    info: LayoutUserInfo | null
    menuItems?: LayoutUserMenuItem[]
  }
  onToggleLocale?: () => void
  header?: LayoutHeaderConfig     // see 3.Header.md
  /** @deprecated Prefer `header.endActions`. */
  headerActions?: ReactNode
}
```

## Sub-types

```ts
export type LayoutNavItem = {
  key: string
  label: string                   // Already-translated string
  path?: string                   // Route (leaf)
  icon?: SvgIconComponent
  badge?: number
  children?: LayoutNavItem[]      // Group (opens as flyout / inline tree)
}

export type LayoutBrand = {
  title: string
  subtitle?: string
  footer?: string                 // Shown at the bottom of the expanded sidebar
}

export type LayoutUserInfo = {
  name: string
  role: string
  initials: string
}

export type LayoutUserMenuItem = {
  key: string
  label: string
  icon?: ReactNode
  href?: string                   // Renders as react-router Link
  disabled?: boolean
  onClick?: () => void
  dividerBefore?: boolean         // Reserved for a future divider slot
}
```

The `LayoutChromeLabels` type is a flat record of 40+ pre-translated strings — search placeholder, menu labels,
theme toggle titles, settings-panel copy, etc. It's the single translation surface for the shell.

## Why labels aren't `t(key)`

`@raccoonland/layout` deliberately has **no i18n dependency**. Passing pre-translated strings keeps the package
locale-agnostic and lets a host use whatever i18n stack it likes (react-i18next, format.js, a custom
dictionary — see the sample's `useLayoutChrome`).

## Provider access

```ts
import { useLayoutShell } from '@raccoonland/layout'

const { direction, labels, user, onToggleLocale } = useLayoutShell()
```

Throws if used outside `LayoutShellProvider` — this is a deliberate DX choice so mounting mistakes surface with
a clear message instead of destructuring a `null`.

## Host wiring pattern

The sample's `Samples/Backoffice/src/layout/useLayoutChrome.ts` shows the recommended pattern:

```ts
export function useLayoutChrome() {
  const { t, direction, locale, toggleLocale } = useLocale()

  const navigation = useMemo(() => resolveNavigation(appNavigation, t), [t])
  const brand      = useMemo(() => ({ title: t('appName'), ... }), [t])
  const labels     = useMemo(() => ({ /* 40+ t() calls */ }), [t, locale])

  return { navigation, brand, labels, direction, onToggleLocale: toggleLocale }
}
```

All returned fields are memoized so `LayoutShellProvider.value` (which memoizes on those fields) stays
referentially stable across renders that don't touch locale.

## Design notes

- Every `LayoutNavItem.label` is a **string**, not a `MessageKey`. This keeps the package free of translation
  concerns; the host's `useLayoutChrome` is where `t(labelKey)` runs.
- `settingsPath` is a per-app override for the "Settings" user menu item. Default is `/settings/layout`.
