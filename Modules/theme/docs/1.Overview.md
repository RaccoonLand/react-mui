# 1. Overview

`@raccoonland/theme` is the single source of truth for the RaccoonLand visual language on the web. It supplies:

- A design-token type (`RaccoonTokens`) with `light` and `dark` presets.
- An MUI theme factory (`createRaccoonTheme(direction, mode, overrides?)`) that plugs tokens into `@mui/material`.
- A theme-mode provider (`ThemeModeProvider`) with system-preference detection and cross-tab sync.
- A `useRaccoonTheme()` hook that safely accesses `theme.raccoon` from any consumer.

- **Package:** `@raccoonland/theme`
- **Peer deps:** `react`, `react-dom`, `@mui/material`, `@mui/icons-material`

## Layering

```text
Tokens (light/dark)         → design decisions (colors, gradients, elevations)
  └── createRaccoonTheme    → MUI Theme with tokens attached via `theme.raccoon`
        └── <ThemeProvider>  → propagated to consumers
              └── useRaccoonTheme() / useTheme()
```

## Package boundaries

Owned by this package:

- `RaccoonTokens` type + presets.
- `createRaccoonTheme` (memoized, deep-merges caller overrides).
- `ThemeModeProvider` (light/dark, `system` fallback, `localStorage`, `storage` event sync).
- `useRaccoonTheme` (typed access to `theme.raccoon`).

Deliberately **not** owned:

- Direction (LTR/RTL). Emotion-cache direction lives at the app level because it's coupled to the locale provider.
  Host apps mount their own `DirectionProvider` (see `Samples/Backoffice/src/app/DirectionProvider.tsx`).
- `<ThemeProvider>` itself. This package produces the theme; hosts choose where to mount MUI's provider.

## Why tokens instead of raw MUI palette everywhere

The MUI palette covers primary/secondary/text/background, but the shell needs a handful of colors MUI has no slot for:
`background.header`, `border.glow`, `nav.activeBg`, `nav.activeIndicatorWidth`, `shellGradient`, `overlay`, `input.*`.
Putting them on `theme.raccoon` keeps them typed and discoverable without polluting the MUI palette namespace.
